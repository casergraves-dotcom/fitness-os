# Fitness OS Principles

## North Star

Every major feature should answer:

> **Does this help the user make a better decision today?**

If not, reconsider its priority or whether it belongs in Fitness OS.

## 1. Guide, Do Not Merely Record

Fitness OS should progressively reduce the amount of training planning
the user must do independently.

A successful Today experience answers:

-   What should I do?
-   Why?
-   What if the original plan is not practical?
-   How do I execute it?
-   How does today's decision affect the larger plan?

## 2. Adherence Beats Theoretical Perfection

The best program is not the most sophisticated program on paper. It is
the program that can be followed consistently.

Prefer:

-   Gradual ramps.
-   Clear priorities.
-   Reasonable session lengths.
-   Useful fallback workouts.
-   Recovery-aware adjustments.

Avoid designs that punish missed days or require perfect weeks to make
progress.

## 3. Optimize for Body Composition and Useful Fitness Together

The primary outcome is sustainable fat loss/body-composition
improvement.

Training should simultaneously protect or improve:

-   Muscle and strength.
-   Aerial capacity.
-   Hiking capacity.
-   Snowboarding readiness.
-   Cardiovascular fitness.
-   General physical capability.

Scale weight is evidence, not the entire objective.

## 4. Treat the Whole Week as Training Load

Gym sessions are not the only training.

Fitness OS should account for:

-   Strength training.
-   Running.
-   Aerials.
-   Hiking/walking.
-   Mobility.
-   Recovery.
-   Future relevant activities.

Do not schedule each modality as if the others do not exist.

## 5. Make Disruption Recoverable

Travel, schedule conflicts, poor recovery, and missed gym access are
normal.

The system should respond with:

-   Substitutions.
-   Shortened sessions.
-   Holds.
-   Deloads.
-   Return-to-training ramps.

A disruption should change the plan intelligently rather than destroy
the routine.

## 6. Calm Guidance Over Judgment

Coach/Guide language should be:

-   Clear.
-   Brief.
-   Useful.
-   Non-judgmental.
-   Specific enough to act on.

Avoid guilt, punishment framing, and noisy gamification.

## 7. Show the Minimum Useful Information First

Fitness OS should feel calm and intentional.

Prioritize:

1.  Today's decision.
2.  The next action.
3.  Essential context.
4.  Detail on demand.

Do not make the user interpret a dashboard full of metrics before
knowing what to do.

## 8. Collect Data With a Purpose

Do not add a metric merely because it can be tracked.

Before collecting data, identify:

-   What decision will it improve?
-   How often does it need to be collected?
-   Can it be inferred/imported instead?
-   Is the burden worth the value?

## 9. Reflect to Improve Future Guidance

History and charts are not endpoints.

Reflection should help answer:

-   Is the plan working?
-   Is adherence improving?
-   Is recovery adequate?
-   Is strength being maintained?
-   Is cardiovascular fitness improving?
-   Is body composition moving in the desired direction?
-   Should the next week progress, hold, or recover?

## 10. Private by Default

Personal fitness and recovery data is private.

Future sharing/social features should expose only data deliberately
designed for sharing.

## 11. Local Use Should Survive Network Problems

Core workout/run/check-in behavior should remain useful when cloud
access is temporarily unavailable.

Cloud synchronization enhances continuity; it should not make execution
fragile.

## 12. Build the Core Loop Before Expanding the Surface Area

Until Core Fitness OS v1 can reliably guide, execute, adapt, and
reflect, prioritize core training behavior over:

-   Social expansion.
-   Cosmetic dashboards.
-   Excessive integrations.
-   Real-time synchronization.
-   Novel features without a clear daily-decision benefit.
